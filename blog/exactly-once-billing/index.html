广告计费系统如何做到不丢不重

2026/06/30 11:00 · 436 字 · 约 1 分钟
广告分布式

广告计费是典型的"错一分钱都是事故"的链路：一次点击从发生到扣费，要经过埋点、上报、消息队列、消费、落库、结算六层，任何一层都可能丢、可能重。

先接受一个现实

网络分区下，经典的结论是：精确一次的传输不存在，只存在"至少一次 + 幂等消费"。所以整条链路的设计目标只有一个——让"重复"变得无害。

关键设计：全链路唯一 ID

给每次计费事件一个全局唯一的 billing_id，在埋点侧生成，之后所有环节都用它做幂等键。这一步的前提是 ID 的生成必须无中心瓶颈，常用方案：

  • 雪花算法（够用，注意时钟回拨）；
  • 号段模式（DB 发号段，内存分配）。

幂等落库

消费侧用数据库唯一索引兜底，而不是依赖 MQ 的"恰好一次"：

CREATE TABLE billing_record (
    billing_id  VARCHAR(64) NOT NULL,
    user_id     BIGINT      NOT NULL,
    amount      BIGINT      NOT NULL COMMENT '微分',
    status      TINYINT     NOT NULL,
    created_at  DATETIME    NOT NULL,
    PRIMARY KEY (billing_id)
);

重复消息走 INSERT IGNORE 或捕获唯一键冲突后比对状态，简单粗暴且正确。

对账是最后一道防线

幂等做得再好，也要假设它有失效的一天。T+1 对账两条线：

  1. 上游对下游：曝光/点击侧的日聚合 vs 计费侧的日聚合，差异超过阈值告警；
  2. 资金侧：账户流水余额恒等式校验，期初 + 充值 - 消耗 = 期末，一天跑一次全量。

监控能发现问题，对账能发现"监控以为没问题"的问题。

一点体会

计费系统的复杂度不在技术选型，而在对"钱"的敬畏心：每一条链路都问一句"这条消息丢了会怎样？重了会怎样？"，答案写进设计文档，比任何架构图都有用。
