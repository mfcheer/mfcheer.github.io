# 相册批量上传失败续传

范围：相册页站内上传，保留现有博主认证、30 张上限、JPEG 压缩与 GIF 原格式。说说发布链路不变。

## 状态与数据

沿用当前浏览器的 IndexedDB 图片草稿，每张图片增加 `upload`：稳定 UUID 文件名、压缩后的 Base64、Git blob SHA-1、请求是否尝试过、成功后的仓库路径。压缩结果与请求身份在 PUT 前排队写入，成功后立即保存路径并释放 Base64。原始 File 仍用于预览和恢复。

- 待处理 → 压缩并生成请求身份 → 保存 → 上传 → 保存成功路径。
- 上传失败 → 保留整批草稿与成功路径；继续时按原顺序跳过成功项。
- 上次请求结果不明 → 先 GET 同一路径，SHA 一致视为成功；404 才补传；权限、网络、限流或 SHA 不一致则停止。
- 全部照片上传成功 → 在文字草稿保存发布批次 ID 与核对起始时间 → POST 相册 Issue。
- 创建请求失败 → 冻结文字和选图，允许保存关闭、重新登录及继续；继续时分页核对本人全部状态的 Issue 中的隐藏批次标记。找到则完成清理，没找到才重试创建。
- 创建成功 → 先保存成功标记，再清空图片草稿，最后清空文字。清理中断后只继续清理。

展示每张成功图片的“已上传”、完成数量与继续按钮。上传期间禁用编辑、关闭与重复提交，保留原有离开页面保护。

## 失败边界

续传粒度是一张照片：中断的单张会重新发送整个文件，不是字节级分块续传。只恢复同一浏览器、同一站点保存的草稿；清除站点数据或换设备无法恢复。存储失败使用现有明确提示与离开保护，不能承诺刷新恢复。清空或移除草稿图片不会自动删除已上传的仓库文件。

GitHub 创建 Issue 没有客户端幂等键。本方案通过请求前保存标记、直接分页核对 Issue 降低响应丢失后的重复概率，不承诺跨窗口并发、远端请求尚未落地时的严格 exactly-once。核对失败绝不盲目 POST。
