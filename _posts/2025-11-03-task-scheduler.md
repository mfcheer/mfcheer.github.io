做过一个支撑日均千万级任务的任务调度平台，把设计要点沉淀一下。真正难的从来不是"定时触发"，而是失败之后怎么办。

## 先想清楚需求边界

调度平台的常见形态有三种，边界完全不同：

| 形态 | 典型场景 | 核心难点 |
|------|---------|---------|
| 定时任务 | 报表生成、数据清理 | 触发精度、重复执行 |
| 工作流编排 | ETL 依赖链 | DAG 调度、断点恢复 |
| 延迟队列 | 订单超时关闭 | 时间轮精度、海量桶 |

多数团队的真实需求是第一种加一点第三种，直接上 Airflow 级别的编排引擎属于过度设计。

## 三个核心抽象

平台侧只需要三个概念：**任务定义**（做什么）、**调度策略**（何时做）、**执行记录**（做得怎么样）。所有花活都应该挂在这三个抽象上，而不是造第四个概念。

## 幂等是地基

分布式调度逃不开的一个问题：worker 拿到任务后，调度器失联了怎么办？恢复后任务是继续还是重来？

答案是：**执行侧幂等，重试就不可怕**。业务键 + 执行批次号做唯一约束，重复投递直接吞掉：

```java
// 幂等表：唯一索引 (task_id, batch_no)
try {
    idempotentDao.insert(taskId, batchNo);
} catch (DuplicateKeyException e) {
    log.warn("duplicate dispatch, task={}, batch={}", taskId, batchNo);
    return; // 重复投递，直接放弃
}
// 走正常执行流程
```

## 失败处理的三层策略

1. **瞬时失败**：网络抖动、下游超时，指数退避重试 3 次；
2. **持续失败**：重试耗尽，进死信队列，人工介入；
3. **雪崩保护**：同一任务连续失败超过阈值，自动熔断并告警，而不是无脑重试打挂下游。

## 可观测性不是附属品

调度平台的用户体验，一半在可观测性上。执行耗时分布、失败 Top 任务、队列积压曲线，这三个面板做完，半夜的告警电话至少少一半。
